# TEST_PLAN

상태: 테스트 계획. 2026-09-28 Vitest + 실제 PostgreSQL을 사용하는 DB 통합 검증 방향을 채택했다. 도메인 시나리오는 계획이며, 실제 실행 명령·검증 환경·결과는 각 PR의 `Test Result`에 기록한다.

## 1. 테스트 단계

- Unit Test
- Integration Test
- System / E2E Test

### Unit
- 정상 착수
- 차례 위반
- 중복 위치

- 통계 계산

### Integration
- Authentication → DB
- Game Command → Engine → Persistence
- WebSocket → Broadcast
- Game Result → Statistics

## 2. 검증 환경

- 별도 개발/검증 DB와 실행 서버를 사용한다. 화면 mock·가짜 API 응답·통계 하드코딩은 완료 증거로 금지한다.
- `qa-p1`, `qa-p2`, `qa-p3`, `qa-p4`는 각각 별개 가입 계정이다. `qa-outsider`는 해당 경기/채팅에 참가하지 않은 계정이다. 실제 userId와 가입에 사용한 테스트 이메일은 검증 환경에서 정하고 기록한다.
- 10/01 B가 가입 API로 계정을 생성하고, A가 로그인·표시 이름을 확인한다. 비밀번호·세션·토큰은 비공개 테스트 환경 설정에 두고 증거·Git·스크린샷에 넣지 않는다.
- 사용 서버 URL·인증서 신뢰 설정·브라우저 버전·실행 commit을 기록한다. 원격 플레이는 실제 PC 2대의 식별명도 기록한다.
- 통계 검증 데이터는 테스트 계정으로 실제 경기 명령을 통해 만든다. unit fixture를 DB에 넣은 결과만으로 통계 모듈을 통과시키지 않는다.
- DB를 초기화해야 한다면 검증 전용 DB임을 확인하고 별도 run을 시작한다. 사용자 운영 DB를 지우지 않는다.

연결 유예 60초·지연 300ms·2개 동시 방·10경기 데이터는 팀의 검증 조건이며 과제 문서의 지정 수치가 아니다. 무효 경기는 참여 진행도·승률·순위에서 제외하고, 무승부는 완료 경기 수에 포함하며 승률은 승수/완료 경기 수로 정의한다. 동일 승수 순위는 닉네임·userId 순으로 고정한다. 게임 중 한 플레이어가 끊기면 일시정지하고 복귀 시 재개한다. 모든 사용자 세션이 사라져야 오프라인으로 본다.

## 5. 백엔드·DB 통합 검증 계획

도구는 기존 Vitest를 사용하고 DB 제약조건·잠금·rollback은 분리된 실제 PostgreSQL에서 검증한다. 개발·공유 DB와 구분한 테스트 연결 설정을 사용하며, 새 테스트 DB에 커밋된 migration을 적용해 준비한다. DB 대체 구현만으로 PostgreSQL 동작을 검증했다고 보지 않는다.

아래 B-IT ID는 백엔드 내부 테스트 ID다. 공식 시스템 시나리오 T00~T10을 대체하지 않으며, 평가 증거에는 별도 실제 서버 검증이 필요하다.

| ID | 검증 | 기대 결과 | 관련 |
|---|---|---|---|
| B-IT-01 | 빈 테스트 DB에 migration 적용 후 ORM 저장·조회 | 테이블·관계·제약조건이 재현되고 저장값 조회 가능 | T00·T01 |
| B-IT-02 | 동일 이메일로 동시 가입 | 사용자 한 건만 저장, 다른 요청은 중복 오류 | T01 |
| B-IT-03 | 하나의 트랜잭션에서 여러 저장 후 의도적으로 실패 | 해당 처리의 변경 전체 rollback, 부분 저장 없음 | T01·T05 |
| B-IT-04 | 같은 원문 비밀번호의 별도 해시 생성·검증과 사용자 저장 경로 확인 | 해시는 서로 다르고 올바른 원문만 검증; DB·응답·로그에 원문 없음 | T01 |
| B-IT-05 | 유효한 JWT로 만료·폐기된 서버 세션에 접근 | 새 보호 요청 거절; 다른 유효 세션 영향은 확정된 로그아웃 범위에 따름 | T01 |
| B-IT-06 | 별도 DB 연결에서 같은 commandId·내용을 동시에 처리 | 착수·버전 변경 한 번, 명령 기록 한 건; 응답은 합의된 재전송 정책 준수 | T04·T05 |
| B-IT-07 | 동일 경기·expectedVersion의 서로 다른 유효 명령을 별도 연결에서 동시에 처리 | 하나만 상태 변경, 나머지는 버전 충돌; 부분 저장 없음 | T05 |
| B-IT-08 | 종료 명령 중복·경합 처리 | 경기·참가자 결과가 한 번만 확정되고 서로 일치 | T07·T08 |
| B-IT-09 | 한 경기의 행 잠금을 유지하며 다른 경기 변경 | 다른 경기의 처리가 첫 경기 잠금에 막히지 않음 | T05 |
| B-IT-10 | DB 접근 불가·서버 종료 | DB health는 503, 내부 연결 정보 노출 없음; 정상 종료 시 Pool 정리 | T00 |

경합 테스트는 독립 DB 연결과 제어 가능한 동기화 지점을 사용해 실제로 요청이 겹치도록 구성한다. 단순 순차 호출이나 시간 지연만으로 경합 검증을 대신하지 않는다. 각 테스트는 데이터를 격리하고 완료 후 테스트 대상만 정리해 반복 실행 결과를 일정하게 유지한다.

서버 세션 상세 스키마·토큰 교체 정책·게임 응답 계약이 미정인 항목은 합의 후 테스트 입력과 정확한 응답 검증을 구체화한다. 각 시나리오의 실행 여부와 결과는 PR의 `Test Result`에서 구분한다.
