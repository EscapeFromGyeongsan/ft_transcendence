## 2. 검증 환경

- 별도 개발/검증 DB와 실행 서버를 사용한다. 화면 mock·가짜 API 응답·통계 하드코딩은 완료 증거로 금지한다.
- `qa-p1`, `qa-p2`, `qa-p3`, `qa-p4`는 각각 별개 가입 계정이다. `qa-outsider`는 해당 경기/채팅에 참가하지 않은 계정이다. 실제 userId와 가입에 사용한 테스트 이메일은 검증 환경에서 정하고 기록한다.
- 실행 서버를 준비한 뒤 B가 `QA_PASSWORD`를 설정하고 `npm run qa:accounts`로 계정을 생성한다. A가 로그인·표시 이름을 확인한다. 비밀번호·세션·토큰은 비공개 테스트 환경 설정에 두고 증거·Git·스크린샷에 넣지 않는다.
- 사용 서버 URL·인증서 신뢰 설정·브라우저 버전·실행 commit을 기록한다. 원격 플레이는 실제 PC 2대의 식별명도 기록한다.
- 통계 검증 데이터는 테스트 계정으로 실제 경기 명령을 통해 만든다. unit fixture를 DB에 넣은 결과만으로 통계 모듈을 통과시키지 않는다.
- DB를 초기화해야 한다면 검증 전용 DB임을 확인하고 별도 run을 시작한다. 사용자 운영 DB를 지우지 않는다.

연결 유예는 사용자별·경기별 누적 60초(DEC-03)다. 지연 300ms·2개 동시 경기·10경기 데이터와 함께 팀의 검증 조건이며 과제 문서의 지정 수치가 아니다. 무효 경기는 참여 진행도·승률·순위에서 제외하고, 무승부는 완료 경기 수에 포함하며 승률은 승수/완료 경기 수로 정의한다. 완료 경기가 1경기 이상인 사용자만 게임별 순위에 포함한다. 동일 승수는 승률 내림차순, 승률도 같으면 userId 오름차순으로 정한다(DEC-08). 닉네임은 정렬 기준이 아니다. 게임 중 한 플레이어가 끊기면 일시정지하고 복귀 시 재개한다. 사용자의 유효한 인증 WebSocket 연결이 모두 사라져야 오프라인으로 본다.

### 3.1 좌표 및 확장 시나리오

- 오목은 `(row, col) = 0..14`, 오델로는 `0..7`이며 `(0, 0)`은 좌상단이다. 현재 보드의 좌표·접근성 라벨과 전송 명령은 모두 0-based다. 과거 1-based T03 수순을 직접 전송하지 않는다.
- T01 확장: TOTP 설정·활성화·로그인 검증·복구 코드 1회 사용·해제, 42 OAuth 로그인·기존 계정 연결·취소·잘못된 state를 검증한다. 실 42 앱 검증에는 별도 앱 설정이 필요하며 `fake42` 테스트 결과로 대체하지 않는다.
- T03 오델로 변형: 별도 두 세션으로 오델로를 매칭한다. 중앙 `(3,3)` 백, `(3,4)` 흑, `(4,3)` 흑, `(4,4)` 백 및 흑 선공을 확인한다. 흑 `(2,3)` 착수 후 `(3,3)`이 흑으로 바뀌어 양쪽 보드와 흑 4개/백 1개가 일치해야 한다. 상대가 둘 수 없으면 자동 패스로 같은 차례가 유지되고, 양쪽 모두 둘 수 없으면 `disc_count` 또는 `draw`로 1회 종료되는 수순도 C와 준비한다.
- T06 친구 초대 변형(서버·UI 구현 후): 친구 요청·수락 후 목록을 다시 읽고 온라인 상태를 확인한다. 거절 전 재요청 차단 안내, 거절한 쪽의 검색·프로필 재요청 동선, `REQUEST_DECLINED` 표시를 확인한다. 친구 초대 수락 즉시 같은 경기로 진입하고, 60초 만료·취소·대기열과의 경합을 검증한다. 친구 계약의 미합의 항목은 SDS 2.10.29·5장을 따른다.
- T09 약관·프로필 UI 변형: 비로그인·로그인 상태에서 `/terms`, `/privacy` 직접 접근·푸터·가입 화면 링크·뒤로가기를 확인한다. T02의 닉네임·아바타 저장 후 새로고침 유지와 로그아웃·기권·2FA 해제 모달의 `Escape` 닫기·포커스 복귀도 확인한다. `recordsPublic` 수정과 회원 탈퇴는 API 구현 후 T02에 추가한다.

## 5. 백엔드·DB 통합 검증 계획

도구는 기존 Vitest를 사용하고 DB 제약조건·잠금·rollback은 분리된 실제 PostgreSQL에서 검증한다. 개발·공유 DB와 구분한 테스트 연결 설정을 사용하며, 새 테스트 DB에 커밋된 migration을 적용해 준비한다. DB 대체 구현만으로 PostgreSQL 동작을 검증했다고 보지 않는다.

아래 B-IT ID는 백엔드 내부 테스트 ID다. 공식 시스템 시나리오 T00~T10을 대체하지 않으며, 평가 증거에는 별도 실제 서버 검증이 필요하다.

|---|---|---|---|
| B-IT-01 | 빈 테스트 DB에 migration 적용 후 ORM 저장·조회 | 테이블·관계·제약조건이 재현되고 저장값 조회 가능 | T00·T01 |

경합 테스트는 독립 DB 연결과 제어 가능한 동기화 지점을 사용해 실제로 요청이 겹치도록 구성한다. 단순 순차 호출이나 시간 지연만으로 경합 검증을 대신하지 않는다. 각 테스트는 데이터를 격리하고 완료 후 테스트 대상만 정리해 반복 실행 결과를 일정하게 유지한다.

서버 세션 상세 스키마·토큰 교체 정책·게임 응답 계약이 미정인 항목은 합의 후 테스트 입력과 정확한 응답 검증을 구체화한다. 각 시나리오의 실행 여부와 결과는 PR의 `Test Result`에서 구분한다.
