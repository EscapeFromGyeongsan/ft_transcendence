# 사이버 보드게임 카페: 5인 실행 로드맵

- 수정 기준일: **2026-10-06**. 모든 날짜·시각은 한국 시간(KST).
- 기능 개발: **10/07~10/24**, 기능 완성·통합 및 동결: **10/24 18:00**.
- 집중 테스트·결함 수정: **10/25~10/31의 7일**. 최종 제출 준비 판정: **10/31 18:00**.
- 제품 범위: **오목 + 2인 오델로**, OAuth·2FA, 공통 계정·프로필·친구·게임별 자동 매칭/친구 초대 대기방·원격 플레이·재접속·게임별 전적/통계. **채팅은 후속 범위**.
- 제출 목표: 공통 필수 요건 + [최신 SRS v0.3 §3](SRS.md)의 **Major 6개 + Minor 4개 = 16점**. 오델로·OAuth·2FA는 모두 16점 목표의 기본 작업이다. 학교 최소 목표 14점과 팀의 16점 완성 목표를 구별한다.
- 이 문서는 요청자의 범위·일정 수정 지시를 반영한 실행 계획이다. 팀 합의·실제 구현·검증 통과를 대신하지 않는다. 카드의 상태는 증거 확인 전까지 `계획`이다.
- 학교 제출 마감은 미확인이다. 10/31 18:00은 내부 준비 목표이며 공식 제출 시각을 새로 정한 것이 아니다. 공식 마감이 더 이르면 일주일 테스트 기간까지 포함해 일정을 다시 조정한다.

## 1. 기준선과 실행 조건

### 문서와 현재 상태

- 기능·모듈·수용 기준의 기준선은 [SRS v0.3](SRS.md)다. 요구사항과 승인 대기 정책은 SRS의 FR/NFR/CON/DATA/DEL 및 DEC ID로 추적한다.
- 과제 근거는 저장소의 [en.subject.pdf](../en.subject.pdf), v21.1이다. 캠퍼스 현재 배정 버전·evaluation sheet·모듈 인정 해석은 DEC-11에서 별도 확인한다.
- 모듈 ID·기능 정책·역할 확인은 GitHub `codex/srs-draft`의 SRS v0.3과 일치시킨다. 기존 로드맵의 주차별 일정을 10/24 기능 완성·10/25~31 테스트 일정으로 재산정한다. 이 계획은 팀 기준선 승인이나 학교 검증을 의미하지 않는다.
- 현재 체크아웃은 문서 중심이며 팀원 브랜치의 구현을 모두 반영한 상태인지 확인되지 않았다. SRS에 적힌 PR #2 기반도 현재 병합·수정 완료 상태를 보장하지 않는다. **10/07에 각자가 실제 브랜치·PR·실행 결과를 공유해 출발 상태를 확인한다.**
- 이미 완료된 작업은 실제 PR/commit·실행 기록을 연결해 재사용한다. 확인하지 않은 기능을 완료 처리하거나 기존 코드가 전부 없다고 가정하지 않는다.

### 가능한 일정의 조건과 시간 예산

- 1인 주 **30시간 이상(권장 30~35시간)** 확보를 계획 가정으로 둔다. 10/07~24는 18일로, 주 30시간이면 1인 약 **77시간**, 5인 약 **386시간**이다. 실제 가능 시간은 아래 표에서 별도 확인한다.
- 개발 카드 예산은 총 **296시간**이며 설계·구현·리뷰·통합·담당자 기본 검증을 포함한다. 최소 가정 대비 약 **90시간(23%)**을 지연·결함·인계 여유로 둔다. 시간은 완료를 보장하는 견적이 아니다. OAuth·2FA·최신 정책을 포함하면서 기존 주 25시간 가정은 B의 64시간 예산을 거의 전부 소진하므로 현실성의 하한을 주 30시간으로 올렸다. 실제 확보가 안 되면 일정 회복 계획을 다시 계산한다.
- 하루 평균을 균등하게 요구하지 않는다. 개인 일정과 휴무를 반영해 10/07에 날짜별 가용시간을 공유하고, 담당자 자신의 여유가 부족하면 재배정한다.
- 일정 성립 조건: 10/08 공통 기반·OAuth/2FA 정책·오델로 상세 계약 확정, 10/13 오목 한 판 저장, 10/18 두 게임 정상 통합, 10/24 전체 기능 완료.
- 두 번째 게임은 SRS에서 확인한 **오델로(리버시), 8×8·2인·흑 선공**이다. 8방향 뒤집기·자동 패스·양쪽 합법 수 없음·돌 수 승패/동수 무승부를 구현한다. 게임 선정은 다시 하지 않으며 팀 기준선 검토와 세부 설계만 10/08까지 마친다.
- OAuth 제공자·계정 연결, 2FA 방식·복구/기존 세션 정책은 DEC-04로 10/08까지 확정한다. E/B가 실제 제공자 개발 설정·테스트 계정·callback URL 준비를 챙긴다. 실제 외부 인증 없이 mock만 통과하면 MOD-09는 미완료다.
- 10/25부터 새 기능·새 게임·새 모듈을 개발할 시간을 배정하지 않는다. 구현 중 기본 검증은 계속하며, 마지막 일주일은 집중 인수·회귀·수정에 사용한다.

## 2. 사람과 단일 책임

최신 SRS의 확정 역할인 **jyoo(sunbear)=UI/UX**를 보존하고 C/D의 공동 표기를 나눈다. A는 jyoo, E는 실행·소셜 역할로 정리한다. **dong-hki의 개발 역할은 기존 확인대로 미정이며 E 배정은 이번 일정의 제안**이다. PO·PM·문서/인수 취합도 제안이며 팀 확정으로 표현하지 않는다. E 실명 확정 전에는 5번째 담당자가 해당 56시간을 실제 맡아야 이 일정이 성립한다. **yoshin=C, sipyeon=D는 이번 수정의 제안이며 실제 팀 합의가 확인된 사실로 기록하지 않는다.** 10/07 각자가 담당을 확인하고, 실제 분담이 반대면 C/D 실명과 해당 카드의 책임자를 함께 바꾼다. 가능 시간도 확인 전에는 가정이다.

| 코드 | 담당자 | 주당 가능 시간 | 조직 역할 | 최종 책임 영역 | 백업 |
|---|---|---|---|---|---|
| A | jyoo(sunbear), UI/UX 확정 | 미확인 / 계획 가정 30~35h | UI/UX, PO·인수 취합 제안 | 가입·OAuth/2FA·공통 화면, 게임 선택/매칭·초대 대기방, 프로필·통계 UI, 정책 페이지 | E |
| B | yunhpark | 미확인 / 계획 가정 30~35h | Tech Lead | 인증·OAuth/2FA·프로필 API, DB/ORM, 원자적 저장·중복/경합 방지, 게임별 통계 API | D |
| C | yoshin (제안 배정) | 미확인 / 계획 가정 30~35h | 게임 개발 | 두 게임 규칙·엔진·결과 판정, 오목/오델로 게임 보드 구현, 게임 규칙 설명 | B |

- 책임자는 **한 명**이며 구현·리뷰 요청·통합·검증·증거까지 챙긴다. 다른 사람의 협업으로 최종 책임을 공동 표기로 바꾸지 않는다.
- A가 전체 UI/UX·인증/프로필/통계 화면을 소유하고, C는 A의 화면 설계에 맞춰 두 게임 보드를, E는 친구·초대 화면을 구현한다. 게임 판정은 C의 서버 엔진만 사용한다.
- E가 친구 관계를 구현하고 D가 계정별 유효 접속 집계를 제공한다. B는 인증·권한·스키마 변경을 리뷰한다.
- A의 문서 취합과 E의 일정 추적은 카드 예산에 포함한다. 각자가 자기 기술 설명·테스트 기록을 작성한다.
- PR은 작성자 외 한 명이 리뷰한다. 인증·스키마·공통 계약 변경에는 B를 추가하되 모든 PR 승인을 B에게 몰지 않는다.

## 3. 범위와 16점 구성

### 기본·축소·후속 범위

| 구분 | 이번 제출 범위 | 완료에 포함할 조건 |
|---|---|---|
| 기본 | 이메일·비밀번호와 OAuth 로그인·2FA 설정/추가 인증/복구, 프로필·아바타·친구·온라인 상태 | 인증·서버 권한·입력 검증·영속화, 기본 아바타, 친구 요청/수락/거절/삭제 |
| 기본 | 게임 선택·규칙 안내, 게임별 자동 매칭·친구 초대 대기방 | 정원·준비·시작·초대/매칭 취소 경합, 다중 기기에서도 활성 참가 위치 하나 |
| 기본 | 오목 + 2인 오델로 | 각각 실제 원격 완주·기권·종료·재접속·결과 저장 |
| 기본 | 게임별 전적·통계·업적/진행도·리더보드 | 반복 조회/종료에 중복 증가 없음, 게임 간 집계 격리 |
| 기본 | 전체 서비스 컨테이너·HTTPS/WSS, 반응형·접근성, 정책 페이지·영어 README | 새 환경 기동과 제3자 재현, 공통 필수 충족 |
| 축소 | 오목 15×15 자유룰, 흑 선공, 5개 이상 승리, 금수·무르기 없음 | FR-OMK 및 DEC-02, 금수·장목 제한을 추가할 경계 설명 |

| 후속 | 기본/고급 채팅, 읽음·차단·채팅 내 초대 | 이번 일정·16점·인수 시나리오에서 제외 |

오델로를 제외하면 다른 모듈이 모두 완성돼도 후보 합계는 **14점**이다. OAuth나 2FA 하나가 빠지면 **15점**, 둘 다 빠지면 **14점**이며 팀의 16점 목표에는 미달이다. 채팅을 빼고도 기존 사용자 교류 Major 점수를 유지하거나 두 번째 게임을 보너스로 다시 돌리지 않는다. 게임별 통계·매칭이 빠진 두 번째 게임은 MOD-06 완료로 보지 않는다.

새 정책은 SRS의 승인 대기 상태를 유지한다. 아래는 결정 **책임자와 마감**을 배정하는 것이며 미정 정책을 이미 승인한 것으로 바꾸는 것이 아니다. 승인된 결정은 같은 PR에서 SRS와 설계 문서에 반영한다.

## 7. 검증 상태와 증거

| 상태 | 조건 |
|---|---|
| 계획 / 작업 중 | 구현 전/진행 중. 점수에 포함하지 않음 |
| 구현됨 | 리뷰·통합 완료, 담당자가 실제 계정/서버/DB로 정상 및 주요 실패 경로 확인 |
| 평가 가능 | 작성자 이외가 SRS의 관련 AT를 재현하고 필수 실패/경합 조건까지 증거로 확인 |
| 내부 검증 실패 | 기대 결과와 불일치. 카드 재개, 해당 모듈 미완료 |
| 학교 기준 확인 대기 | 내부 검증과 학교 평가표 대조를 구별해 기록 |

- `qa-p1~p4`는 별도 가입 계정, `qa-outsider`는 경기/친구 관계에 속하지 않은 계정으로 사용한다. B가 10/13까지 실제 가입 API로 준비한다. 비밀번호·토큰은 비공개 테스트 환경에만 둔다.
- 새 환경·서버 URL·브라우저·실제 PC 식별·검증 commit·roomId/matchId·게임 종류를 기록한다. mock/하드코딩·DB fixture만으로 실제 게임 완료 증거를 대신하지 않는다.
- 증거 위치: `evidence/<카드 또는 AT-ID>/<YYYYMMDD-HHMM>/`. `run.md`에 사전 조건/입력/기대값/실제값/판정/확인자, `test.log`에 민감값 없는 실행 기록, `changes.md`에 PR/commit·파일·리뷰어를 둔다. 화면 증거는 필요한 경우 사진 또는 영상 하나를 연결한다.
- 시나리오는 [SRS §9 AT-01~17](SRS.md)를 사용한다. 별도 T 번호 체계를 중복 유지하지 않는다. 카드→요구사항→AT→증거→commit을 연결한다.
- 마일스톤에서는 이미 유효한 증거를 재사용한다. 변경 영향이 있는 경로는 다시 확인하되 모든 기능을 매일 반복 촬영하지 않는다. 문서 수정으로 가짜 테스트 기록·완료 표시를 만들지 않는다.

## 8. 병목·지연 시 대응

- E의 배포·친구/초대·탈퇴 처리를 단계별로 나눴다. 배포가 지연되면 A가 실행 재현·문서/화면 작업을 맡고, 서버 권한·스키마 문제만 B와 협업한다. 오델로 규칙 구현을 E에게 추가하지 않는다.
- C/D가 반나절 이상 막히면 B가 원인 재현·계약/저장 검토를 지원한다. 지원 시간을 기록하고 통계 장식·추가 필터 등 미계획 작업을 늘리지 않는다.
- 10/08 OAuth/2FA 정책·실제 제공자 준비/오델로 계약 실패, 10/13 한 판 저장 실패, 10/18 두 게임 정상 통합 실패는 **10/24 완성 위험**으로 표시한다. E가 다음 날 12:00까지 남은 작업·가용시간·회복 카드·영향 날짜를 갱신한다.
- 지연 시 디자인 장식·추가 옵션·미채택 편의 기능을 먼저 줄이고 다른 사람이 실행 가능한 작은 작업을 재배정한다. 두 번째 게임·게임별 매칭/통계·아바타/친구/초대·OAuth/2FA·누적 이탈 복구·필수 보안을 지우면서 16점을 유지하지 않는다.
- 실제 가용시간이 계획보다 적거나 두 번째 게임의 난도가 예산을 넘으면 일정 또는 모듈 대체를 별도 결정한다. OAuth/2FA를 자동으로 제외하거나 채팅 Major로 변경하거나 테스트 주간을 기능 개발로 바꾸는 결정을 자동 적용하지 않는다.
