# 사이버 보드게임 카페: 5인 실행 로드맵

- 계획 기준일: 2026-09-20. 모든 마감·회의 시각은 한국 시간(KST).
- 개발 기간: 2026-09-21~2026-10-31. 기본 기능 구현 목표 10/11, 평가 가능 목표 10/18, 제출 후보 고정 10/29.
- 제품 목표: 오목 1개를 제공하는 턴제 게임 플랫폼. 계정·방·경기 저장·재접속·전적을 공통화하고 게임 규칙·화면을 분리한다.
- 제출 목표: 공통 필수 요건 + 선택 모듈 14점. 윷놀이는 조건부 보너스이며 기본 일정에 개발 시간을 배정하지 않는다.
- 현재 상태: 이 파일은 실행 계획이다. 구현·테스트·평가 통과를 보고하는 문서가 아니다. 모든 카드의 초기 상태는 `계획`이다.
- 파일 이력: 작업 공간에 기존 `Document/roadmap.md`가 없어, 대화의 기존 로드맵을 아래 수정안으로 파일화했다.

## 1. 변경 원칙과 현실성

1. 3주차에 기능 개발과 평가를 동시에 끝내지 않는다. 친구·채팅의 정상 경로는 2주차, 재접속·통계 구현은 3주차, 오류 처리와 모듈별 증빙은 4주차로 나눈다.
2. D는 방·경기 실행·실시간 상태 복구에 집중한다. DB 동시성·중복 요청은 B, 초기 컨테이너·HTTPS는 E가 맡는다. D의 실시간 백업은 B, E의 배포 백업은 A다.
3. E는 친구·채팅 구현과 가벼운 일정 운영을 맡는다. 통합 테스트는 영역별 담당자, README·모의 평가 취합은 A가 맡는다.
4. 기능의 `구현됨`과 `평가 가능`을 분리한다. 실제 계정·실제 서버·실제 DB로 제3자가 재현해야 평가 가능하다.
5. 선택한 모듈의 필수 세부 조건을 삭제하면서 점수는 유지하지 않는다. 14점 미달이나 일정 실패는 그대로 표시한다.

### 작업 시간 가정

- 1인 주 25~30시간 확보를 가정한다. 9/21 18:00까지 이름·가능 시간을 아래에 채운다.
- 계획에 배정하는 개발·검증은 1인 주 약 18~22시간, 나머지는 학습·리뷰·결함 수정 여유다. 각 카드의 예산은 보장 시간이 아닌 상한 관리용 추정이다.
- 휴무·개인 일정으로 첫 주 가용 시간이 줄어들면 즉시 반영한다. 남는 일이 자동으로 야간·주말에 해결된다고 가정하지 않는다.
- 마일스톤 지연 시 신규 범위를 줄인다. 그래도 14점이 불가능하면 E가 다음 날 12:00까지 `14점 미달 위험`, 영향 모듈, 필요한 추가 시간을 기록한다.

### 최종 책임과 백업의 의미

- **책임자:** 구현·검증·증거 제출까지 챙기는 한 명. 협업자가 있어도 완료 여부가 모호해지지 않는다.
- **백업:** 담당 코드 실행·핵심 흐름 설명·작은 수정이 가능해야 한다. 단순 참조 인원이 아니다.
- **리뷰어:** 작성자 외 한 명. 모든 PR을 B가 승인할 필요는 없다. 인증·스키마·공통 계약 변경만 B를 추가한다.
- **평가 확인자:** 작성자 이외의 사람이 증거 묶음의 시나리오를 실제 서버에서 재현한다.

## 6. 증거 규격과 실제 계정

### 검증 환경

- 별도 개발/검증 DB와 실행 서버를 사용한다. 화면 mock·가짜 API 응답·통계 하드코딩은 완료 증거로 금지한다.
- `qa-p1`, `qa-p2`, `qa-p3`, `qa-p4`는 각각 별개 가입 계정이다. `qa-outsider`는 해당 경기/채팅에 참가하지 않은 계정이다. 실제 userId와 가입에 사용한 테스트 이메일은 검증 환경에서 정하고 기록한다.
- 9/27 B가 가입 API로 계정을 생성하고, A가 로그인·표시 이름을 확인한다. 비밀번호·세션·토큰은 비공개 테스트 환경 설정에 두고 증거·Git·스크린샷에 넣지 않는다.
- 사용 서버 URL·인증서 신뢰 설정·브라우저 버전·실행 commit을 기록한다. 원격 플레이는 실제 PC 2대의 식별명도 기록한다.
- 통계 검증 데이터는 테스트 계정으로 실제 경기 명령을 통해 만든다. unit fixture를 DB에 넣은 결과만으로 통계 모듈을 통과시키지 않는다.
- DB를 초기화해야 한다면 검증 전용 DB임을 확인하고 별도 run을 시작한다. 사용자 운영 DB를 지우지 않는다.

### 증거 묶음

각 카드와 마일스톤은 `evidence/<ID>/<YYYYMMDD-HHMM>/`에 다음을 남긴다. 증거를 생성하는 것은 카드 담당자의 작업에 포함한다.

1. `run.md`: 날짜, 담당자/확인자, 실제 서버 URL, commit, 계정 별칭/userId, matchId/roomId, 사전 조건, 입력 순서, 기대값/실제값, 판정.
2. `test.log`: 시나리오 ID, 실행 입력 요약, 결과, 실제 상태 버전·저장 건수 등. 민감값 제거. 자동화가 없으면 실행자/확인자가 서명한 단계별 실행 로그로 대체한다.
3. `screen.png` 또는 `demo.mp4`: 실제 사용자 화면. 동시에 보는 상태는 두 창 또는 두 PC를 포함한다. 모든 카드에 영상과 사진을 둘 다 요구하지 않는다.
4. `changes.md`: 담당 PR URL 또는 commit SHA, 변경 파일, 리뷰어. 인프라·계약 카드도 실제 서버의 결과 이미지/터미널 캡처를 포함한다.

구현 카드가 여러 시나리오를 포함하면 같은 묶음 안에서 T 번호로 구분한다. 마일스톤은 이미 유효한 증거를 연결하고 필요한 인수 시연만 새로 기록한다. 전부 반복 촬영하지 않는다. 이후 변경이 결과에 영향을 주면 해당 증거를 재검증한다.
