# 사이버 보드게임 카페: 5인 실행 로드맵

- 최초 계획 기준일: 2026-09-20 / 범위 수정일: 2026-10-04. 모든 마감·회의 시각은 한국 시간(KST).
- 개발 기간: 2026-09-21~2026-10-31. 기본 기능 구현 목표 10/11, 평가 가능 목표 10/18, 제출 후보 고정 10/29.
- 제품 목표: 오목과 2인 오델로를 제공하는 플랫폼. 계정·친구·자동 매칭·친구 초대 대기방·경기 저장·재접속을 공통화하고 게임별 규칙·화면·전적/통계를 구분한다.
- 제출 목표: 공통 필수 요건 + OAuth·2FA 포함 선택 모듈 16점 후보(과제 최소 14점). 채팅은 후속 제안이며 기본 점수에 포함하지 않는다. 윷놀이와 다인전은 이번 초안에서 제외한다.
- 현재 상태: 이 파일은 실행 계획이다. 구현·테스트·평가 통과를 보고하는 문서가 아니다. 모든 카드의 초기 상태는 `계획`이다.
- 파일 이력: 기존 14점·오목/채팅 계획을 [SRS v0.3](SRS.md)와 [이슈 #3 팀원 의견](https://github.com/EscapeFromGyeongsan/ft_transcendence/issues/3#issuecomment-5945171542), 2026-10-04 요청자 답변에 맞춰 범위를 수정했다.

> 범위는 요청자가 확인한 검토용 초안이며 팀 전체의 승인·구현 완료를 의미하지 않는다. 기존 주차별 날짜·시간 예산은 재산정 전 계획이다. 오델로·OAuth·2FA와 UI 변경의 추가 작업이 기존 예산에 들어간다고 가정하지 않는다. 이 문서 수정으로 과거 마감이나 인수 상태를 완료로 바꾸지 않는다.

## 1. 변경 원칙과 현실성

1. 3주차에 기능 개발과 평가를 동시에 끝내지 않는다. 친구·경기 초대의 정상 경로는 기존 2주차 목표, 재접속·통계는 기존 3주차 목표다. 오델로·OAuth·2FA의 구현·오류 처리·증빙 예산과 인계 날짜는 추가 카드에서 팀이 재산정한다.
2. D는 방·경기 실행·실시간 상태 복구에 집중한다. DB 동시성·중복 요청은 B, 초기 컨테이너·HTTPS는 E가 맡는다. D의 실시간 백업은 B, E의 배포 백업은 A다.
3. E는 친구·경기 초대 구현과 가벼운 일정 운영을 맡는 기존 역할 제안을 유지한다. 통합 테스트는 영역별 담당자, README·모의 평가 취합은 A가 맡는다. OAuth·2FA는 팀원 제안대로 B를 담당 후보로 기록하며 마감·예산은 확정하지 않는다.
4. 기능의 `구현됨`과 `평가 가능`을 분리한다. 실제 계정·실제 서버·실제 DB로 제3자가 재현해야 평가 가능하다.
5. 선택한 모듈의 필수 세부 조건을 삭제하면서 점수는 유지하지 않는다. 14점 미달이나 일정 실패는 그대로 표시한다.

### 작업 시간 가정

- 1인 주 25~30시간 확보를 가정한다. 9/21 18:00까지 이름·가능 시간을 아래에 채운다.

- 서브젝트 검토 후 팀원이 제안한 모듈 구성이 타당하다고 판단하여 제안한 방향으로 수정했다. 기존 14점 구성에 OAuth·2FA 각 Minor 1점을 추가한 16점 구성을 반영하고, 채팅은 후속 검토 항목으로 유지한다. 캠퍼스 적용 조건과 실제 인정 여부는 REQ-00/SRS DEC-11에서 확인한다.
- MOD-01에 프런트·백 Minor를 다시 더하지 않는다. 친구/프로필만으로 사용자 교류 Major를 계산하지 않는다.
- MOD-02는 대기방·초대·접속 상태, MOD-05는 실제 원격 경기·복구로 구분해 증명한다. 중첩 인정의 로컬 해석은 REQ-00에서 확인한다.
- MOD-06은 실제 오델로·매칭·전적/통계가 필요하다. 메뉴 이름만 추가하거나 오목의 스킨만 바꾼 결과는 완료가 아니다.
- 추가 두 Minor가 있어도 오델로 미완성은 목표 기능 미완성이다. 완전한 게임/원격 플레이/통계 등 다른 미완성 조건도 각각 0점으로 계산한다.
- 업적 한 개로 별도 Gamification, 아바타만으로 File upload, 게임별 폴더로 Microservices 점수를 주장하지 않는다.

## 6. 증거 규격과 실제 계정

### 검증 환경

- 별도 개발/검증 DB와 실행 서버를 사용한다. 화면 mock·가짜 API 응답·통계 하드코딩은 완료 증거로 금지한다.
- `qa-p1`, `qa-p2`, `qa-p3`, `qa-p4`는 각각 별개 가입 계정이다. `qa-outsider`는 해당 경기나 친구 초대의 참가 대상이 아닌 계정이다. 실제 userId와 가입에 사용한 테스트 이메일은 검증 환경에서 정하고 기록한다.
- 9/27 B가 가입 API로 계정을 생성하고, A가 로그인·표시 이름을 확인한다. 비밀번호·세션·토큰은 비공개 테스트 환경 설정에 두고 증거·Git·스크린샷에 넣지 않는다.
- 사용 서버 URL·인증서 신뢰 설정·브라우저 버전·실행 commit을 기록한다. 원격 플레이는 실제 PC 2대의 식별명도 기록한다.
- 통계 검증 데이터는 테스트 계정으로 실제 경기 명령을 통해 만든다. unit fixture를 DB에 넣은 결과만으로 통계 모듈을 통과시키지 않는다.
- DB를 초기화해야 한다면 검증 전용 DB임을 확인하고 별도 run을 시작한다. 사용자 운영 DB를 지우지 않는다.

### 증거 묶음

각 카드와 마일스톤은 `evidence/<ID>/<YYYYMMDD-HHMM>/`에 다음을 남긴다. 증거를 생성하는 것은 카드 담당자의 작업에 포함한다.

1. `run.md`: 날짜, 담당자/확인자, 실제 서버 URL, commit, 계정 별칭/userId, matchId/roomId, 사전 조건, 입력 순서, 기대값/실제값, 판정.
2. `test.log`: 시나리오 ID, 실행 입력 요약, 결과, 실제 상태 버전·저장 건수 등. 민감값 제거. 자동화가 없으면 실행자/확인자가 서명한 단계별 실행 로그로 대체한다.
3. `screen.png` 또는 `demo.mp4`: 실제 사용자 화면. 동시에 보는 상태는 두 창 또는 두 PC를 포함한다. 모든 카드에 영상과 사진을 둘 다 요구하지 않는다.
4. `changes.md`: 담당 PR URL 또는 commit SHA, 변경 파일, 리뷰어. 인프라·계약 카드도 실제 서버의 결과 이미지/터미널 캡처를 포함한다.

구현 카드가 여러 시나리오를 포함하면 같은 묶음 안에서 T 번호로 구분한다. 마일스톤은 이미 유효한 증거를 연결하고 필요한 인수 시연만 새로 기록한다. 전부 반복 촬영하지 않는다. 이후 변경이 결과에 영향을 주면 해당 증거를 재검증한다.
