# 이슈 #7 실행 환경 작업 계획

- 작성일: 2026-10-12 (한국 시간, Asia/Seoul)
- 작업 브랜치: `codex/full-app-containers`
- 기준 커밋: `d4a939fea197d78f066e20e66cb6279cc3520c9e` (`master`)
- 작업 범위: 이슈 #7의 웹·API·DB 전체 컨테이너화와 HTTPS 실행 환경
- 게시 제한: PR 생성·병합·이슈 종료·리뷰어 메시지 전송을 하지 않는다.

## 진행 순서

1. 전체 앱 실행용 Compose 진입점을 별도로 추가하고, npm workspace를 기준으로 재현 가능한 이미지를 구성한다.
2. DB 준비 확인·기존 migration 적용·API 준비 확인을 연결하고 기존 로컬 기본값을 유지한다.
3. 빌드된 웹 파일·API·Swagger를 HTTPS로 제공하고 WebSocket upgrade 전달 설정을 준비한다.
4. 인증서·비밀번호 준비, 환경 변수 우선순위, 기동·종료·재생성 방법과 격리된 검증 절차를 문서화한다.
5. 변경 내용을 검토하고, 실제 확인한 결과와 남은 검증 항목을 기록한 뒤 요청자에게 보고한다.

## 작업 범위와 원칙

- 게임·인증·소셜 기능이나 실제 WebSocket endpoint를 구현하지 않는다.
- 공유된 migration, 의존성 버전, 기존 개발용 Compose 데이터를 변경하지 않는다.
- 전체 앱은 별도 Compose 프로젝트·볼륨을 사용한다. 첫 기동과 실패 상황 검증은 추가로 격리한 검증용 프로젝트에서 수행한다.
- 실제 비밀번호·개인키·인증서를 커밋하지 않는다.
- 프록시 설정 준비를 실제 WSS 검증 완료로 취급하지 않는다.
- 실행 증거와 작성자 외 팀원의 재현 결과가 없으면 수용 기준을 완료로 표시하지 않는다.

## 작업 환경과 실행 방법

최초 작업에서는 로컬 도구 오류로 원격 브랜치에 초안과 문서를 저장했다.
이번 검증에서는 승인 검토를 거친 로컬 셸 실행이 가능함을 확인하고, 원격 커밋을 변경 없는 로컬 브랜치에 fast-forward했다.
이후 작업은 로컬에서 진행했으며 추가 push·PR 생성은 하지 않았다.

기존 DB·개인 설정 파일을 보존하기 위해 고유한 검증 프로젝트 네 개와 별도 환경 파일·인증서를 사용했다.
자동 승인 서비스의 일시적인 429 오류는 대기 후 승인된 재시도로 해소했다.
기본 샌드박스 셸과 Windows Node 파일 도구의 기존 오류가 해결됐다고 주장하지 않는다.

## 이번 작업의 진행 상태

- 1~4단계: 구현·설정·한글 실행 안내 작성 완료
- 5단계: 실제 빌드·기동·HTTPS·브라우저·장애·데이터 보존·기존 개발 회귀 검증과 증거 기록 완료
- 검증에서 발견한 수정: 문서의 프로젝트 디렉터리와 맞도록 Compose 빌드 context 두 곳을 `.`로 변경
- 실행 코드 커밋: `9dc764ad5327a3de66bfe0186124a807519df8f5`
- 정리: 새 검증용 프로젝트만 제거, 기존 DB 컨테이너·볼륨 유지
- 남은 확인: 작성자 외 팀원 재현, Windows 브라우저 CA 신뢰 설정, 실제 endpoint 인계 후 WSS
- 저장 위치: 동기화된 로컬 브랜치. 추가 변경은 로컬 커밋만 작성
- PR: 생성하지 않음. 자체 검증 결과상 리뷰를 받을 단계

공유 migration·의존성·도메인 기능은 변경하지 않았으며 처음 정한 실행 환경 범위를 유지했다.
명령·환경·결과·한계는 [실제 검증 기록](runtime-validation.md)에 남긴다.
