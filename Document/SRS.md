## 1. 목적과 문서 경계

이 문서는 여러 보드게임을 하나의 계정과 공통 이용 흐름으로 제공하는 웹 플랫폼의 요구사항을 정의한다. 이후 SDS의 구성 요소, 데이터 모델, 인터페이스, 상태 전이, 테스트 설계가 이 문서의 요구사항 ID를 참조하도록 한다.

SRS는 사용자가 할 수 있는 일, 허용·거절 조건, 데이터 보존과 품질 조건을 규정한다. 구체적인 테이블·컬럼, URL, 메시지 형식, 인증 구현 방식, 클래스·디렉터리 구조는 SDS에서 설계한다. 현재 기반의 health API는 현황이며 향후 전체 API 설계를 확정하지 않는다.

### 1.2 표기와 승인 의미

- **필수:** PDF 공통 필수 조건. 제품 범위 결정과 관계없이 충족해야 한다.

요구사항은 ID별로 추적한다. 각 표의 수용 기준은 해당 요구사항의 최소 확인 조건이며, 테스트 실행 결과가 아니다. 이번 문서에는 제품 기능에 대한 실행 완료 체크를 표시하지 않는다.

## 2. 제품 개요

### 2.1 제품 목표

사용자는 동일한 계정으로 게임을 선택하고 상대와 연결되어 원격 경기를 진행하며, 게임별 결과와 자신의 전적을 확인할 수 있어야 한다. 게임이 추가되어도 계정·프로필·친구를 다시 생성하지 않아야 한다. 게임별 규칙과 승패 조건은 공통 플랫폼 기능과 분리하여 설명할 수 있어야 한다.

플랫폼의 성공 기준은 메뉴에 여러 게임이 표시되는 것이 아니라, 제출 범위에 포함된 각 게임을 실제 서로 다른 컴퓨터에서 시작·완료하고 해당 게임의 결과를 다시 조회할 수 있는 것이다.

### 2.2 사용자와 권한

| 행위자 | 허용 범위 | 제한 |
|---|---|---|
| 비로그인 방문자 | 가입·로그인, 서비스 소개·게임 규칙·약관·개인정보처리방침 열람 | 경기 참가·친구 변경·개인 데이터 변경 불가 |
| 로그인 사용자 | 자기 프로필 관리, 게임 선택·방/매칭 이용, 친구·전적 이용 | 타인 계정·비공개 정보 변경 불가 |
| 경기 참가자 | 자신이 참가한 경기의 허용된 행동과 상태 조회 | 상대 대신 행동하거나 다른 경기 변경 불가 |
| 방 생성자 | 시작 조건이 충족된 대기방의 시작 요청 | 게임 중 규칙 변경·임의 결과 확정 권한 없음 |
| 운영·평가 담당자 | 문서화된 설치·기동·검증 수행 | 관리자 제품 UI는 별도 범위 결정 전 미포함 |

### 2.3 현재 구현과 목표의 차이

채택 예정 기반에는 React·Vite, Fastify·TypeScript, PostgreSQL·Drizzle, npm workspaces, 상태 확인 API, Swagger, 테스트 설정이 있다. 사용자 화면은 제목 표시 수준이며 사용자·방·경기 데이터 모델과 게임 기능은 포함되어 있지 않다. 공통 게임 패키지는 빈 틀이다.

2026-09-29 별도 작업 공간의 해당 PR 커밋에서 의존성 설치·DB 기동·마이그레이션·DB 확인·빌드·API 테스트 4개를 재현했다. E2E 2개는 WSL의 `libasound.so.2` 누락으로 브라우저 시작 전에 실패했다. 이 결과는 향후 제품 요구사항의 통과 근거가 아니다. 현재 로컬 HTTP 개발 구성이 PDF의 HTTPS 및 전체 앱 컨테이너 요구를 충족한다는 뜻도 아니다.

2026-09-30 KST에 등록된 요청자의 PR 코멘트는 같은 커밋에 대한 **별도의 검증 기록**이다. 해당 기록의 API 테스트는 실제 PostgreSQL 없이 `app.inject()`로 수행했고, Swagger 응답 정의 확인도 실제 브라우저 UI 확인과 구별한다. 이 기록을 앞선 DB 포함 실행 결과와 합쳐 하나의 검증처럼 표현하지 않는다.

해당 코멘트에는 API 시작 실패 후 하위 Vite 프로세스가 남는 문제와, 루트 `.env`의 `PORT` 변경이 Vite 프록시에 반영되지 않는 문제가 보고되어 있다. 따라서 기본 설정의 정상 실행 성공만으로 종료·실패 처리와 비기본 포트까지 검증됐다고 해석하지 않는다. 이 초안은 이를 NFR-OPS-02, CON-06, AT-14에 반영하며, 구체적인 코드 수정과 재검증은 PR #2에서 추적한다. 문서 수정 시 PR HEAD는 여전히 `dcb2488`이며 수정 완료로 판정하지 않았다.

## 3. 범위와 선택 모듈

### 3.1 공통 제출 범위

- 이메일·비밀번호 가입/로그인 및 권한 확인.
- 공통 프로필·친구·온라인 상태.
- 여러 게임을 보여주는 게임 목록과 게임별 규칙 안내.
- 게임별 방·상대 매칭, 원격 경기, 접속 해제와 복귀 처리.
- 게임별 결과·전적·통계·업적/진행도·리더보드.
- 반응형·기본 접근성, 정책 페이지, 암호화된 외부 연결.
- 전체 서비스의 컨테이너 기동, 초기화·검증·운영 문서.

요청자가 선택한 초안 범위는 오목과 미정의 두 번째 게임, 후보 A 14점이며 채팅은 후속 범위다. 팀의 최종 승인은 아래 결정 기록에서 관리한다. 하나의 게임을 완성한 것만으로 여러 게임 플랫폼 또는 두 번째 게임 모듈을 완료 처리하지 않는다.

### 3.3 기본 제외 범위

팀이 별도로 채택하기 전에는 AI 상대, 토너먼트, 관전, OAuth, 2FA, 관리자 콘솔, 결제, 게임 재화, 3D 그래픽, 일반 파일 관리, 추가 언어, 전용 모바일 앱을 포함하지 않는다. 두 번째 게임의 다인 플레이 여부는 게임 선정 후 별도 결정한다. 이 제외 목록이 과제 공통 필수인 반응형·보안·접근성을 면제하지 않는다.

### 5.7 후속 범위: 채팅

FR-CHAT-01(송수신), FR-CHAT-02(대화 접근 제어), FR-CHAT-03(재접속 후 메시지 처리)은 향후 변경을 위한 예약 ID이며 이번 14점 후보의 인수 범위가 아니다. 현재 채팅 기능이나 사용자 교류 Major를 구현·선택했다고 표시하지 않는다. 추후 채택 시 수신 대상, 기록 보존, 오프라인 처리와 수용 기준을 먼저 추가한다.

두 번째 게임의 이름과 규칙은 **미정**이다. 이 문서는 게임이 구현될 자리를 정의하지만 가상의 규칙으로 상세 설계를 완료하지 않는다. DEC-01이 해결되기 전에는 이 절·MOD-06·해당 게임 SDS를 승인 완료할 수 없다.

| FR-G2-01 | 게임명, 오목과 구별되는 핵심 규칙, 인원·역할·팀 여부, 초기 상태 | 게임별 규칙 문서와 화면 설명이 일치하며 오목의 스킨 변경에 그치지 않는다. |
| FR-G2-02 | 차례·행동·불법 행동·승/패/무승부·기권·중단 조건 | 정상 완주와 각 불법/종료 경로에 대해 입력과 기대 결과가 작성되어 있다. |

### 10.2 추적 레코드

GitHub 이슈·PR과 SDS에서 다음 항목을 연결한다. 아래는 형식 예시이며 아직 생성하지 않은 이슈/PR 번호를 꾸며 넣지 않는다.

```text
요구사항 ID: FR-OMK-03
근거: SRS 6.1 / DEC-02
상태: 초안 / 승인 / 설계 / 구현 / 검증
관련 결정: DEC-02
SDS 절: 작성 후 연결
구현 이슈 / PR / 커밋: 생성 후 연결
검증: AT-05 + 게임 규칙 테스트
실제 결과 / 확인자 / 검증 커밋: 실행 후 기록
```

SRS 변경은 요구사항 ID·변경 이유·영향받는 게임/설계/테스트를 기록한다. 삭제한 ID는 재사용하지 않는다. GitHub에서 합의하고 승인한 문서를 기준으로 삼으며, 이 문서 자체로 Project·마일스톤·리뷰 규칙을 새로 생성하거나 기존 팀 운영을 덮어쓰지 않는다.

### 11.1 확인된 오목 재접속 정책의 세부 동작

- 경기 진행 중 필요한 참가자의 접속 해제를 서버가 감지하면 경기를 일시정지하고 참가자에게 유예 상태를 알린다. 감지 방식과 최대 감지 지연은 SDS에서 명시한다.
- 유예 시간은 서버가 일시정지를 시작한 시각부터 60초이다. 두 번째 참가자의 추가 이탈이나 상태 조회·중복 연결 요청은 진행 중인 유예를 연장하지 않는다.
- 유예 안에 두 참가자가 모두 정상 접속하면 최신 상태를 동기화하고 같은 경기·차례로 재개한다. 정지 중 입력은 경기 상태를 변경하지 않는다.
- 유예 만료 시 한 명만 접속해 있으면 부재자 패배, 두 명 모두 부재하면 무효로 종료한다. 재개·만료가 경합하면 서버가 하나의 결과만 결정하고 모두에게 일치하게 전달한다.
- 종료 후 복귀한 사용자는 종료 이유와 결과를 확인한다. 무효 경기는 진행 이력과 사유를 확인할 수 있으나 승패·업적 진행·순위에는 포함하지 않는다(통계 세부 정책은 DEC-08 승인 대상).
- 명시적인 기권은 별도의 종료 행동이다. 탭 종료·네트워크 단절만으로 즉시 기권으로 처리하지 않는다.
- 서버가 죽은 경우의 복구는 연결 유예와 구별하며 DEC-07이 확정되어야 한다. 이 정책만으로 서버 재시작 복구가 구현되었다고 간주하지 않는다.

### 11.2 SRS 검토 체크리스트

- [ ] 팀이 제품 범위와 14점 후보의 각 모듈·의존 조건을 검토했다.
- [ ] 두 번째 게임의 DEC-01 및 FR-G2-01~05가 구체화되었다.
- [ ] DEC-04~10 중 SDS의 외부 동작을 좌우하는 정책을 확정하거나 명시적으로 연기했다.
- [ ] 요구사항별 수용 기준으로 정상·예외·동시 요청을 판정할 수 있다.
- [ ] 게임 규칙 확장 요구가 SDS에서 검증 가능한 책임 경계로 연결된다.
- [ ] PDF 공통 필수와 선택 모듈 조건이 빠지지 않았다.
- [ ] 미구현·미검증·학교 기준 미확인을 완료로 표현하지 않았다.
- [ ] 작성자 외 검토자와 팀 승인 기록을 연결했다.

미정인 두 번째 게임을 제외한 공통 부분의 SDS 초안은 병행할 수 있다. 다만 아직 정하지 않은 인원·정보 공개·종료/통계 정책을 하드코딩한 설계를 최종 확정하지 않는다.
