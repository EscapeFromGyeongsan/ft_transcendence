## 1. 목적과 문서 경계

이 문서는 여러 보드게임을 하나의 계정과 공통 이용 흐름으로 제공하는 웹 플랫폼의 요구사항을 정의한다. 이후 SDS의 구성 요소, 데이터 모델, 인터페이스, 상태 전이, 테스트 설계가 이 문서의 요구사항 ID를 참조하도록 한다.

SRS는 사용자가 할 수 있는 일, 허용·거절 조건, 데이터 보존과 품질 조건을 규정한다. 구체적인 테이블·컬럼, URL, 메시지 형식, 인증 구현 방식, 클래스·디렉터리 구조는 SDS에서 설계한다. 현재 기반의 health API는 현황이며 향후 전체 API 설계를 확정하지 않는다.

### 1.2 표기와 승인 의미

- **필수:** PDF 공통 필수 조건. 제품 범위 결정과 관계없이 충족해야 한다.

- **미정:** 구현 결과를 판정할 수 있을 정도의 결정이 아직 없는 항목. 연결된 요구사항을 완료·승인 상태로 표시하지 않는다.

요구사항은 ID별로 추적한다. 각 표의 수용 기준은 해당 요구사항의 최소 확인 조건이며, 테스트 실행 결과가 아니다. 이번 문서에는 제품 기능에 대한 실행 완료 체크를 표시하지 않는다.

## 2. 제품 개요

### 2.1 제품 목표

사용자는 동일한 계정으로 게임을 선택하고 상대와 연결되어 원격 경기를 진행하며, 게임별 결과와 자신의 전적을 확인할 수 있어야 한다. 게임이 추가되어도 계정·프로필·친구를 다시 생성하지 않아야 한다. 게임별 규칙과 승패 조건은 공통 플랫폼 기능과 분리하여 설명할 수 있어야 한다.

플랫폼의 성공 기준은 메뉴에 여러 게임이 표시되는 것이 아니라, 제출 범위에 포함된 각 게임을 실제 서로 다른 컴퓨터에서 시작·완료하고 해당 게임의 결과를 다시 조회할 수 있는 것이다.

### 2.2 사용자와 권한

| 행위자 | 허용 범위 | 제한 |
|---|---|---|
| 비로그인 방문자 | 가입·로그인, 서비스 소개·게임 규칙·약관·개인정보처리방침 열람 | 경기 참가·친구 변경·개인 데이터 변경 불가 |
| 로그인 사용자 | 자기 프로필 관리, 게임 선택·방/매칭 이용, 친구·전적 이용 | 타인 계정·비공개 정보 변경 불가 |
| 경기 참가자 | 자신이 참가한 경기의 허용된 행동과 상태 조회 | 상대 대신 행동하거나 다른 경기 변경 불가 |
| 방 생성자 | 시작 조건이 충족된 대기방의 시작 요청 | 게임 중 규칙 변경·임의 결과 확정 권한 없음 |
| 운영·평가 담당자 | 문서화된 설치·기동·검증 수행 | 관리자 제품 UI는 별도 범위 결정 전 미포함 |

### 2.3 현재 구현과 목표의 차이

채택 예정 기반에는 React·Vite, Fastify·TypeScript, PostgreSQL·Drizzle, npm workspaces, 상태 확인 API, Swagger, 테스트 설정이 있다. 사용자 화면은 제목 표시 수준이며 사용자·방·경기 데이터 모델과 게임 기능은 포함되어 있지 않다. 공통 게임 패키지는 빈 틀이다.

2026-09-29 별도 작업 공간의 해당 PR 커밋에서 의존성 설치·DB 기동·마이그레이션·DB 확인·빌드·API 테스트 4개를 재현했다. E2E 2개는 WSL의 `libasound.so.2` 누락으로 브라우저 시작 전에 실패했다. 이 결과는 향후 제품 요구사항의 통과 근거가 아니다. 현재 로컬 HTTP 개발 구성이 PDF의 HTTPS 및 전체 앱 컨테이너 요구를 충족한다는 뜻도 아니다.

2026-09-30 KST에 등록된 요청자의 PR 코멘트는 같은 커밋에 대한 **별도의 검증 기록**이다. 해당 기록의 API 테스트는 실제 PostgreSQL 없이 `app.inject()`로 수행했고, Swagger 응답 정의 확인도 실제 브라우저 UI 확인과 구별한다. 이 기록을 앞선 DB 포함 실행 결과와 합쳐 하나의 검증처럼 표현하지 않는다.

해당 코멘트에는 API 시작 실패 후 하위 Vite 프로세스가 남는 문제와, 루트 `.env`의 `PORT` 변경이 Vite 프록시에 반영되지 않는 문제가 보고되어 있다. 따라서 기본 설정의 정상 실행 성공만으로 종료·실패 처리와 비기본 포트까지 검증됐다고 해석하지 않는다. 이 초안은 이를 NFR-OPS-02, CON-06, AT-14에 반영하며, 구체적인 코드 수정과 재검증은 PR #2에서 추적한다. 문서 수정 시 PR HEAD는 여전히 `dcb2488`이며 수정 완료로 판정하지 않았다.

## 3. 범위와 선택 모듈

### 3.1 공통 제출 범위

- 이메일·비밀번호 가입/로그인 및 권한 확인.
- 공통 프로필·친구·온라인 상태.
- 여러 게임을 보여주는 게임 목록과 게임별 규칙 안내.
- 게임별 자동 매칭·친구 초대 대기방, 원격 경기, 접속 해제와 복귀 처리.
- 외부 계정 로그인(OAuth)·2FA 설정과 검증. 제공자·복구 방식은 DEC-04에서 결정.
- 게임별 결과·전적·통계·업적/진행도·리더보드.
- 반응형·기본 접근성, 정책 페이지, 암호화된 외부 연결.
- 전체 서비스의 컨테이너 기동, 초기화·검증·운영 문서.

2026-10-04 요청자가 확인한 수정 초안 범위는 오목과 2인 오델로, OAuth·2FA를 더한 16점 후보이며 채팅은 후속 제안이다. 팀원 의견과 요청자의 초안 확인을 구분하고, 팀의 최종 승인은 결정 기록에서 관리한다. 하나의 게임을 완성한 것만으로 여러 게임 플랫폼 또는 두 번째 게임 모듈을 완료 처리하지 않는다.

서브젝트 검토 후 팀원이 제안한 모듈 구성이 타당하다고 판단하여, 제안한 방향으로 초안을 수정했다. 기존 14점 구성에 OAuth·2FA 각 Minor 1점을 추가해 **16점 구성**으로 반영했으며, 채팅은 후속 검토 항목으로 유지한다. 이 구성은 2026-10-04 요청자가 확인한 초안 범위이며, 캠퍼스 적용 조건과 실제 인정 여부는 DEC-11에서 확인한다. 제공자·2FA 방식과 복구 정책은 DEC-04에서 확정한다. B의 구현 담당 제안을 기록하되 추가 예산·인계·마감은 팀에서 정한다.

기본 채팅을 포함하는 사용자 교류 Major(p.12)는 이번 범위와 점수에 포함하지 않는다. 채팅은 여유가 생길 때 추가 점수 후보로 검토하며, 채택하려면 프로필·친구·기본 채팅 전체의 수용 기준과 일정부터 확정한다. 16점 계획만으로 점수 여유가 확보됐다고 판단하지 않는다.

프런트·백 프레임워크 Major와 같은 프레임워크 Minor를 중복 합산하지 않는다. 아바타만으로 파일 관리 모듈을, 업적 일부만으로 별도 Gamification 모듈을 주장하지 않는다. 두 번째 게임은 첫 게임이, 통계 모듈은 완전한 게임이 먼저 필요하다. 미완성 모듈은 0점이다(PDF p.10~11). 학교의 실제 인정 여부는 시연과 평가로 확인하며 후보 합계만으로 14점 달성을 선언하지 않는다.

### 3.3 기본 제외 범위

팀이 별도로 채택하기 전에는 AI 상대, 토너먼트, 관전, 관리자 콘솔, 결제, 게임 재화, 3D 그래픽, 일반 파일 관리, 추가 언어, 전용 모바일 앱, 공개방 목록·임의 방 참가, 랭크 기반 매칭, 비밀번호 방·초대 링크를 포함하지 않는다. 오목과 오델로는 모두 2인 1:1이며 팀전·다인전은 제외한다. OAuth·2FA는 16점 후보에 포함한다. 이 제외 목록이 과제 공통 필수인 반응형·보안·접근성을 면제하지 않는다.

| UC-04 | 준비 → 시작 → 게임 행동 → 결과 | 동일 경기 상태와 최종 결과를 참가자에게 제공 | 차례 밖 행동, 불법 행동, 중복·오래된 요청 |
| UC-05 | 경기 중 연결 해제 → 복귀 | 동일 계정이 같은 경기의 최신 상태로 복귀 | 유예 만료, 모두 이탈, 서버 재시작 |
| UC-06 | 전적·통계·진행도·리더보드 조회 | 선택한 게임의 결과를 일관되게 조회 | 경기 없음, 무효 경기, 반복 조회 |
| UC-07 | 친구 요청 → 수락/거절 → 상태 조회 → 삭제 | 양쪽 관계와 접속 상태가 일치 | 자신에게 요청, 중복·교차 요청 |
| UC-08 | 상대 선택 → 채팅 전송·수신 | 권한 있는 대화 참가자만 메시지 확인 | 수신 대상 오류, 연결 해제, 권한 없는 조회 |

UC-08은 후속 채팅 기능을 별도 채택하는 경우에만 적용한다. ‘준비’, ‘진행 중’, ‘종료’의 세부 상태 전이와 프로토콜은 아래 동작 제약을 유지하면서 SDS에서 정의한다.

팀원 제안의 비밀번호 정책은 8~128자·문자 조합 강제 없음, 다중 기기 허용, 현재 기기 세션만 로그아웃이다. 이 정책과 로그인 수명은 DEC-04에서 팀 승인한다. 검증 규칙은 클라이언트와 서버가 일치해야 한다. Argon2id 해시와 JWT access 30분·refresh 7일·서버 세션은 팀원이 제안한 SDS 설계 방향으로 기록하며, 테이블·토큰 저장/회전·폐기·비용값을 이 문서에서 확정하지 않는다. JWT의 만료만 기다리는 방식으로 FR-AUTH-03의 로그아웃 요구를 축소하지 않는다.

메일 기반 소유 확인·비밀번호 복구·이메일 변경, OAuth 제공자와 계정 연결, 2FA 방식·복구·설정 변경 시 기존 세션 처리는 회의 결정 항목이다. 이메일·비밀번호 가입/로그인을 OAuth로 대체하지 않으며, 학교 평가표에서 추가 메일 요건이 있는지는 DEC-11로 확인한다.

친구 기능만으로 사용자 교류 Major를 주장하지 않는다. 해당 Major에는 기본 채팅까지 필요하다.

초안은 공개방 없이 같은 게임/규칙의 대기 순서를 기준으로 자동 매칭하고, 수락된 친구를 직접 초대하는 두 경로를 제공한다. 대기방은 두 경로의 내부 경기 준비 상태이며 공개 탐색 대상이 아니다. 친구 초대 대기방의 생성자 퇴장 시 권한 이전 없이 폐쇄한다. 자동 매칭의 시작 요청 주체·준비 절차·색상 배정, 친구 초대 유효기간은 DEC-06과 SDS에서 상세화하며 UI 담당 검토는 대기이다. 두 게임 모두 실제 매칭을 인수해야 한다.

| FR-G2-05 | 기권·일시 단절·복귀·유예 만료·서버 재시작은 두 게임의 공통 정책을 적용한다. | 명시적인 기권은 기권자 패배다. 재접속은 같은 경기·색상·돌 배치·차례/패스·결과를 복원하고 불필요한 새 경기·중복 패스를 만들지 않는다. 이탈은 DEC-03, 재시작 무효는 DEC-07을 따른다. 상대 비공개 패나 난수로 규칙 결과를 정하지 않는다. |

게임 화면과 사전 규칙 안내는 위 판정과 일치해야 한다. 모든 뒤집기 방향, 복수 방향 동시 뒤집기, 한쪽 자동 패스, 보드 포화 전 양쪽 행동 불가, 동수 무승부는 입력·기대값이 작성된 합법 시나리오로 검증한다. 색상 배정·준비/시작 절차는 DEC-06에서 두 게임에 일관되게 적용한다.

### 10.2 추적 레코드

GitHub 이슈·PR과 SDS에서 다음 항목을 연결한다. 아래는 형식 예시이며 아직 생성하지 않은 이슈/PR 번호를 꾸며 넣지 않는다.

```text
요구사항 ID: FR-OMK-03
근거: SRS 6.1 / DEC-02
상태: 초안 / 승인 / 설계 / 구현 / 검증
관련 결정: DEC-02
SDS 절: 작성 후 연결
구현 이슈 / PR / 커밋: 생성 후 연결
검증: AT-05 + 게임 규칙 테스트
실제 결과 / 확인자 / 검증 커밋: 실행 후 기록
```

SRS 변경은 요구사항 ID·변경 이유·영향받는 게임/설계/테스트를 기록한다. 삭제한 ID는 재사용하지 않는다. GitHub에서 합의하고 승인한 문서를 기준으로 삼으며, 이 문서 자체로 Project·마일스톤·리뷰 규칙을 새로 생성하거나 기존 팀 운영을 덮어쓰지 않는다.

### 11.1 요청자가 확인한 두 게임의 재접속 정책

- 서버가 오목·오델로 참가자의 유효한 경기 제어 연결 해제를 감지하면 경기를 일시정지한다. 감지 방식·최대 감지 지연·시간 계산 기준은 SDS에서 정의한다.
- 부재 시간은 **사용자별·경기별 누적**한다. 각 사용자는 총 60초의 복귀 예산을 가지며, 서버가 부재를 감지한 시각부터 해당 사용자의 예산을 소모한다. 복귀 시 소모를 멈추되 누적값은 유지하고 다음 부재 때 이어서 계산한다. 새 경기에서는 새 예산을 적용한다.
- 참가자 둘이 동시에 부재하면 각자의 예산을 독립적으로 소모한다. 다른 참가자의 이탈·상태 조회·중복 요청·다중 탭/기기 전환은 이미 쓴 예산을 돌려주지 않는다. 서비스의 다른 로그인 세션만 살아 있다는 이유로 경기 복귀로 처리하지 않는다.
- 각 사용자의 누적 부재가 60초에 도달하기 전에 정상 복귀하고 두 참가자가 모두 경기 제어 연결을 유지하면, 최신 보드·역할·차례를 동기화하여 재개한다. 상대 부재 때문에 정지한 동안 정상 접속 중인 사용자의 예산은 소모하지 않는다. 정지 중 게임 입력은 상태를 바꾸지 않는다.
- 현재 부재 중인 사용자의 누적 예산이 먼저 만료되는 순간, 한 명만 부재하면 그 사용자 패배·상대 승리, 두 명 모두 부재하면 무효로 종료한다. 연결 복구와 만료가 경합해도 서버가 하나의 상태 전이/종료만 확정한다.
- 종료 후 복귀하면 이유와 결과를 표시한다. 무효의 이력과 사유는 확인할 수 있지만 승패·무승부·업적·참여 진행도·순위에는 포함하지 않는다.
- 명시적인 기권은 별도 종료 행동이다. 탭 종료·네트워크 단절은 즉시 기권으로 처리하지 않는다. 서버 재시작으로 중단된 미완료 경기는 DEC-07의 무효 처리로 구별한다.

### 11.2 SRS 검토 체크리스트

- [ ] 팀이 제품 범위와 16점 후보의 각 모듈·의존 조건을 검토했다.
- [ ] 두 번째 게임의 DEC-01 및 FR-G2-01~05가 구체화되었다.
- [ ] DEC-04~10 중 SDS의 외부 동작을 좌우하는 정책을 확정하거나 명시적으로 연기했다.
- [ ] 요구사항별 수용 기준으로 정상·예외·동시 요청을 판정할 수 있다.
- [ ] 게임 규칙 확장 요구가 SDS에서 검증 가능한 책임 경계로 연결된다.
- [ ] PDF 공통 필수와 선택 모듈 조건이 빠지지 않았다.
- [ ] 미구현·미검증·학교 기준 미확인을 완료로 표현하지 않았다.
- [ ] 작성자 외 검토자와 팀 승인 기록을 연결했다.

공통 부분과 오델로의 SDS 초안은 병행할 수 있다. 다만 팀 승인·OAuth 제공자/계정 연결·2FA 복구·메일 기능·개인정보 보존 및 UI 흐름의 미결정 항목을 하드코딩한 설계를 최종 확정하지 않는다.
